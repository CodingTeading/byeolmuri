# 관측 플래너 (2단계)

`apps/web-frontend/src/plugins/planner/` — 사이드 패널 "오늘 밤" 탭.

stellarium-web 이 하지 않는 것을 한다. 원본은 하늘을 보여주기만 하고
"오늘 밤 뭘 볼까"에는 답하지 않는다.

## 무엇을 계산하는가

| 항목 | 방법 |
|---|---|
| 일몰 / 일출 | 태양 고도가 -0.833°(대기굴절+반지름 보정)를 지나는 시각 |
| 천문박명 | 태양 고도 -18° 통과 시각. 이 사이가 진짜 어두운 시간 |
| 달 방해도 | 조명 비율 × 어두운 시간대에 달이 떠 있는 비율 |
| 대상별 최고 고도·최적 시각 | 적경/적위에서 해석적으로 계산 |
| 추천 점수 | 고도 0.45 + 관측 가능 시간 0.2 + 밝기 0.35 (행성 +0.15) |

## 설계 판단

**태양·달은 엔진, 나머지는 해석적 계산.** 태양과 달은 궤도 계산이 필요해
엔진에 맡기고 5분 간격 스캔 + 이분법으로 분 단위까지 좁힌다. 반면 관측
대상은 수백 개라 대상마다 엔진을 호출하면 WASM 왕복이 수천 번 생겨 UI 가
멈춘다. 적경/적위만 한 번 받아오고 고도는 구면삼각법으로 직접 푼다.
서울 기준 전체 계산 154ms.

**후보는 10등급까지.** 소형 망원경 한계선이다. 색인 기준 DSO 524개.
여기에 고도 20° 미만이거나 30분 미만만 보이는 대상은 제외한다.

**listObjs 로 열거한다.** upstream 버그(모든 모듈이 1개만 반환)를 고친
덕분에 가능해졌다. `src/js/obj.js` 참고.

## 주의: 엔진 객체는 반응형이 아니다

앱이 뜨는 순간 엔진은 기본 위치(타이베이)에 있고, 잠시 뒤 지오코딩
결과로 바뀐다. `$stel.core.observer` 를 직접 읽으면 Vue 가 변화를 감지하지
못해 **엉뚱한 위치의 계획을 계속 보여주게 된다.** 실제로 처음 구현에서
서울 사용자에게 타이베이 기준 계획이 나왔다.

반드시 `$store.state.stel.observer` 를 통해 읽어야 한다. 이쪽은 엔진의
onValueChanged 로 갱신되는 반응형 트리다 (`sw_helpers.initStelWebEngine`).

## 기상청 단기예보

`functions/api/forecast.js` — Cloudflare Pages Function 프록시.

브라우저에서 기상청을 직접 부를 수도 있지만(CORS 는 열려 있다) 그러면
**API 키가 번들에 그대로 노출되어** 누구나 우리 일일 할당량을 소진시킬 수
있다. 그래서 프록시를 둔다. 키는 Pages 환경변수 `KMA_API_KEY` 에 있고
저장소에는 없다.

프록시는 캐시도 겸한다. 단기예보는 하루 8번(02,05,08,11,14,17,20,23시)만
갱신되므로 같은 격자 요청은 한 번만 기상청에 나간다.

- 위경도 → 기상청 격자: 람베르트 정각원추도법. 서울 중구 60,127 /
  제주시 53,38 로 표준값과 일치 확인.
- 사용 항목: SKY(하늘상태), PTY(강수형태), POP(강수확률), TMP, REH
- 밤 시간대에 걸치는 예보만 뽑아 평균낸다. 비/눈 예보가 있으면 점수 0.

종합 판정은 구름 0.65 + 달 0.35. 예보를 못 받으면 달만 보고 판단하며,
그 사실을 UI 에 숨기지 않는다 (한반도 밖에서는 예보 자체가 없다).

로컬 dev server 에는 Function 이 없으므로 `vue.config.js` 의 devServer
프록시가 배포본으로 넘긴다.
